1. The Challenge
Every new software project starts with the same question: what should we build it with? The answer
depends on far more than popularity. A three-person student team with no budget, a fintech bound by RBI
data-localisation rules, and a game studio chasing 60 ms latency should not end up with the same stack.
Your task is to build a tech stack recommendation engine. It takes structured project parameters, such
as scale, team size and skills, budget, infrastructure and compliance constraints, and returns a
recommended combination of frontend, backend, database and hosting, plus supporting services where
relevant. Every choice must come with architectural reasoning that a senior engineer would accept.
The engine is judged on whether its recommendations are right for the constraints, whether it asks
for the right inputs, and whether it can explain itself. A beautiful UI that recommends the same
stack for every project will score poorly.

5. Engine Design Rules
5.1 Use of LLMs and AI services
The decision must be yours. The selection of stack components must be made by logic you design:
rules, weighted scoring, decision trees, constraint solving, knowledge graphs, or ML models that you
train or fit yourself on cited data.
LLMs (hosted or local) are permitted only for:
Input parsing: turning the free-text project.description into suggested structured fields, which the
user can confirm or edit.
Wording: rephrasing explanations your engine has already produced, without changing the chosen
components.
LLM-off test: your engine must provide a switch (flag, environment variable or UI toggle) that disables all
LLM calls. With it switched off, the engine must produce the same stack for every scenario. Judges will
run this test. If the stack is chosen by an LLM prompt, the submission receives zero for Recommendation
Quality.
AI coding assistants may be used to write code. Declare them in the report.
5.2 Knowledge base
Build and curate your own representation of technologies: their strengths, limits, cost profile,
operational burden, ecosystem, compliance support and maturity.
Recommend only real, currently maintained products. Recommending deprecated or shut-down
services is penalised.
Cite the sources behind your knowledge base: official docs, pricing pages, surveys, benchmarks,
case studies.
5.3 Hard and soft constraints
Treat data_residency, compliance, deployment_model and an explicit cloud_preference as hard
constraints: a recommendation that breaks them must not be produced, or must be flagged as a critical
warning. Budget, timeline and priorities are soft constraints that your engine trades off and explains.

35% Judges run your engine on the 6 public scenarios and on additional

12. Frequently Asked Questions
Can my engine call ChatGPT, Claude, Gemini or another LLM?
Only for the two permitted uses in Section 5.1: turning a free-text description into structured inputs, and
polishing the wording of explanations. The stack selection itself must be made by your own logic. Your
engine must run with all LLM features switched off and still produce the same stack. If the stack is chosen
by an LLM, the submission receives zero for Recommendation Quality.
Can I use AI coding assistants (Copilot, Cursor, Claude Code, etc.) to write my code?
Yes. Declare which ones you used in the report's AI assistance section. The design decisions, knowledge
base and reasoning must be your own.
Is there one correct stack for each scenario?
No. Judges have a set of acceptable answers per scenario and a list of choices that are clearly wrong for
that scenario. A well-justified, defensible choice scores well even if it differs from the judges' first
preference.
Must I use the exact JSON field names?
Your engine must accept scenario files in the standard schema exactly as specified, because judges will
feed hidden scenarios in that format. Your UI can look however you like, and you may add extra input
fields as long as the engine works when they are absent.
Which technologies must my engine know about?
None are mandated. Coverage and accuracy of your knowledge base are judged. As a guide, a credible
engine usually knows at least 6-8 realistic options for each core layer, plus common supporting services.
Do I need to deploy my engine online?
No. It must run locally using the steps in your README. A hosted demo link is welcome but optional, and it
does not replace the local setup.
Web UI or command line?
Either is acceptable, as long as the engine can load a scenario JSON file and export the output JSON. A
UI usually makes evaluation easier.
Can I use public datasets such as the Stack Overflow Developer Survey, GitHub statistics or cloud
pricing pages?
Yes. Cite every dataset, API and library in the report. Uncited third-party material may be treated as
plagiarism.

How accurate must the cost estimate be?
It is an order-of-magnitude band with stated assumptions. Judges check that it is in the right range for the
scenario, not that it matches a provider's price list to the dollar.
Why is the budget in USD?
Most cloud and SaaS price lists are published in USD. You may additionally display INR in your UI.
What should my engine do when the constraints cannot all be met?
Say so. Returning status "infeasible" with clear critical warnings, or a clearly labelled reduced-scope
recommendation that names the constraints it relaxed, are both valid. A confident answer that ignores the
conflict is not.
Can I use boilerplates or starter templates?
Yes, for scaffolding (for example create-next-app or a Django starter). The recommendation engine itself
must be written during the challenge window.
Can I reuse a project I built earlier?
No. Pre-existing projects lead to disqualification. Open-source libraries are fine when cited.
Can I edit my submission after the deadline?
No. Judges check modification timestamps in the Drive folder. Any file added or changed after 15
